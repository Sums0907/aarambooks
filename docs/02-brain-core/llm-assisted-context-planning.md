# Architecture Impact Report: LLM-Assisted Context Planning

## 1. Original Architecture Assumption
The Brain Core architecture developed through Phases 1–12 implicitly assumed a **deterministic context retrieval model**. 
It assumed that a Natural Language (NL) query would be mapped to a known intent, which would then trigger a predefined, hard-coded request for specific `Context Capabilities` (e.g., "Where is my order?" -> `CUSTOMER_PROFILE` + `ORDER_STATE`). The LLM was solely positioned at the end of the pipeline to reason over the retrieved facts and generate a response.

## 2. Newly Clarified Product Intent
Aaram Brain is intended to answer **arbitrary natural-language questions about the Aaram ecosystem**, including questions the system has never seen before (e.g., "Compare material consumption efficiency across jobwork vendors"). Brain must dynamically understand the question, determine the required evidence, obtain it through a governed mechanism, and synthesize an answer. The 17 sample queries from previous phases were merely validation scenarios, not the boundary of Brain's intelligence.

## 3. Discovered Limitation
Predefined `Context Capabilities` (like `JOBWORK_CONTEXT`) are highly optimized and valuable, but they cannot represent the complete universe of possible queries without creating an unmaintainable, infinite list of APIs. If Brain encounters an arbitrary question that doesn't perfectly align with a predefined capability, the current deterministic architecture simply hits a "Context Capability Gap" and fails. It lacks the cognitive ability to *explore* and *discover* data.

## 4. The New Abstraction: LLM-Assisted Context Planning
To solve this, the architecture introduces a **Cognitive Context Planner**. The LLM is now utilized as a planning component *before* final reasoning.
- **Cognitive Planner:** Decomposes arbitrary NL questions, requests schema/semantic knowledge from Brain Core, generates a dynamic Retrieval Plan, and iteratively requests evidence.
- **Reasoning LLM:** Takes the final assembled Evidence Package and generates the business response.

## 5. Role of Deterministic Orchestration (Context Engine)
The Context Engine (`ContextAssembler`, `ProviderRegistry`) remains critical. It becomes the **controlled execution and retrieval substrate**. The LLM Planner proposes a retrieval plan; the Context Engine validates, authorizes, executes (via governed APIs or semantic read-models), and normalizes the results. The LLM *never* has direct, unconstrained access to a raw production database.

## 6. Predefined Capabilities vs. Dynamic Discovery
These two concepts will coexist in a hybrid model:
- **Predefined Context Capabilities:** Reusable, governed abstractions for frequently needed business truth (e.g., `ORDER_STATE`). The LLM Planner will preferentially select these when they fit the need.
- **Dynamic Context Discovery:** For long-tail or highly specific queries, the LLM Planner can request semantic schema metadata (e.g., "Show me the schema for inventory ledger") and then formulate governed, read-only queries (e.g., using a GraphQL or Semantic Layer interface exposed by the Context Engine) to retrieve ad-hoc facts.

## 7. Schema, Semantics, and Workflow Knowledge
For the LLM Planner to dynamically discover data, Brain Core must provide more than just raw database schemas. It must expose **Business Semantic Knowledge** (e.g., what does a negative quantity mean? What is the workflow from Issue -> Receipt -> Scrap?). This semantic metadata becomes a foundational asset that Brain Core feeds to the LLM Planner to guide its retrieval strategy.

## 8. Iterative Context Construction
Context retrieval is no longer a single-pass operation. 
The architecture must support multi-turn evidence gathering:
1. LLM Planner requests evidence A.
2. Context Engine retrieves A.
3. LLM Planner evaluates A, realizes it now needs evidence B to fully answer the question.
4. Context Engine retrieves B and merges it into the ongoing Evidence Package, preserving provenance.

## 9. Read-Only Data Access Boundary
The system will strictly enforce governed access. Brain will likely interface with business systems through **Semantic Query Services** or **Governed Read-Replicas** using restricted Service Accounts. Queries generated by the LLM Planner are validated for safety (timeouts, read-only constraints, tenant isolation, no full-table scans) before deterministic execution.

## 10. LLM Provider Abstraction
Gemini is treated as a provider, not a permanent architectural dependency. The architecture introduces a **Brain LLM Gateway** concept to abstract the Planner and Reasoner roles, allowing future insertion of open-weight models for bounded tasks while using advanced models for complex cognitive planning.
