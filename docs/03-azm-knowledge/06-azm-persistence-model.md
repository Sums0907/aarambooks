## 1. Logical Persistence Requirements

For Azm to be the "Persistent Ecosystem Knowledge Repository", it must move beyond static Python scripts. The FIRST real persistent Azm system must satisfy the following logical requirements:

### 1.1 What Knowledge Must Persist?
Azm must persist its normalized logical primitives:
- Namespaces / Domains
- Semantic Concepts (Names, Definitions, Aliases)
- Relationships (Concept A -> Concept B)
- Schematic References (Views, APIs)
- Attribute Mappings (Concept -> Field)
- Provenance Metadata

### 1.2 Identity & Versioning
- **Identity:** Every knowledge node must have a permanent UUID generated by Azm upon ingestion. It is entirely independent of the Business System's operational UUIDs.
- **Versioning:** Knowledge is immutable. When a concept's definition changes, a new version of the knowledge node is created, and the old node is marked `archived`.
- **Active State:** Queries from Brain default to resolving against the `ACTIVE` knowledge state unless a specific historical context is requested.

### 1.3 Provenance Tracking
Every row/node in the persistence layer must contain:
- `source_business_system`
- `source_contract_identifier`
- `source_contract_hash_or_version`
- `ingestion_timestamp`

### 1.4 Namespace Representation
Namespaces (e.g., `inventory`, `catalog`) are root nodes in the persistence hierarchy. All concepts belong strictly to one Namespace, enforcing domain boundaries at the database level.

### 1.5 What Must NEVER Persist
- Operational business records (e.g., the actual inventory count of SKU 123).
- Ephemeral transactional states.
- Customer PII.

## 2. Technology Recommendation (Future Decision)

*Note: This is a recommendation based on current project realities, not an architectural invariant.*

**Recommendation: Relational Database (PostgreSQL)**

**Rationale:** 
The knowledge model described above is highly structured, relational, and requires strict ACID compliance for versioning and provenance. Concepts belong to Namespaces, and Mappings link to Schemas. A standard relational schema (e.g., `azm_namespaces`, `azm_concepts`, `azm_relationships`, `azm_schemas`) perfectly satisfies these requirements.

Prematurely adopting Vector Databases, Graph Databases, or LLM embeddings is **rejected** for this phase. The first Azm database must solve *Persistent Governed Knowledge*, not speculative AI infrastructure. Vector search can be layered on top of the relational truth later if semantic drift resolution requires it.
