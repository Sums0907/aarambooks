# Azm Persistence Model

**Document Reference:** `docs/03-azm-knowledge/06-azm-persistence-model.md`
**System Name:** Aaram Zameer (`Azm`)
**Classification:** Foundational Architecture

---

## 1. Logical Persistence Requirements

For Azm to be the "Persistent Ecosystem Knowledge Repository", it must move beyond static Python scripts. The FIRST real persistent Azm system must satisfy the following logical requirements.

---

### 1.1 What Knowledge Must Persist?

Azm's persistent store must represent both **semantic** and **schematic** knowledge as independently addressable, versioned, provenance-tagged entities.

**Semantic Knowledge Primitives:**

| Primitive | What It Represents |
|---|---|
| Namespace / Domain | Boundary of knowledge ownership; classified as `AARAM_NATIVE` or `EXTERNAL_CHANNEL` |
| Semantic Concept | An atomic business idea declared by a BS (e.g., `SKU`, `Product`) |
| Definition | The canonical textual definition of a concept |
| Vocabulary / Alias | Alternative human terms that resolve to a concept |
| Semantic Relationship | A directional link between two concepts (within-BS or cross-BS) |
| External / Channel Mapping | Link from an AARAM_NATIVE concept to an external channel concept |

**Schematic Knowledge Primitives:**

| Primitive | What It Represents |
|---|---|
| Schematic Reference | A governed public surface (SQL view, REST API, MCP schema) exposed by a BS |
| Schematic Attribute | An individual field within a Schematic Reference, with data type and description |
| Attribute Mapping | The explicit link between a Semantic Concept and a Schematic Attribute |

**Provenance & Lifecycle Primitives:**

| Primitive | What It Represents |
|---|---|
| Knowledge Provenance | For Source-Declared: traces BS → Contract → Version → Element. For AZM-Derived: traces [Contract A + Contract B] → Derivation Method |
| Knowledge Version | Immutable version record; concept changes create new versions, old ones archived |
| Lifecycle State | `ACTIVE`, `DEPRECATED`, or `ARCHIVED` — applies to all knowledge primitives |

---

### 1.2 Identity & Versioning

- **Identity:** Every knowledge node must have a permanent UUID generated by Azm upon ingestion. It is entirely independent of the Business System's operational UUIDs or contract file names.
- **Versioning:** Knowledge is immutable. When a concept's definition changes, a new version of the knowledge node is created, and the old node is marked `ARCHIVED`.
- **Active State:** Queries from Brain default to resolving against `ACTIVE` knowledge state unless a specific historical context is requested.
- **Source-Declared vs. Derived:** Both knowledge kinds carry their own provenance. Derived knowledge records its derivation method so AZM can always answer: *"Why does this relationship exist?"*

---

### 1.3 What Must NEVER Persist

- **Operational business records:** (e.g., the actual inventory count of SKU 123). Azm is not a transactional database.
- **BS-internal tables:** Azm does NOT create a table-per-BS mirror merely because a BS has an internal table. Only governed public contract declarations are ingested.
- **Source contract files:** AZM does not store copies of the source Semantic or Schematic contract documents (markdown files, SQL DDL). These remain owned by the Business System. AZM stores the knowledge derived from them.
- **Second copies of operational truth:** AZM knowledge about "which view contains SKU data" is not the same as the actual SKU records. AZM must not become a second source of operational truth.

---

### 1.4 Schematic Knowledge Must Be First-Class

A common simplification risk is persisting schematic knowledge as merely a list of view names (e.g., `vw_catalog_skus`). **This is insufficient.**

Azm must persist individual Schematic Attributes (columns/fields) as first-class knowledge nodes so that Brain Core can answer questions like:
- *"Which field in `vw_catalog_skus` represents selling price?"*
- *"What data type does `sku_id` have in `vw_catalog_skus`?"*
- *"Is the `gross_margin` field derived or stored?"*

Without field-level schematic knowledge, Brain Core cannot construct correct queries without hardcoding field names — which would violate the AZM knowledge boundary.

## 2. Technology (Future Decisions & Open Gaps)

**FUTURE IMPLEMENTATION DECISION — Candidate: Relational Database (PostgreSQL)**

The knowledge model described above is highly structured, relational, and requires strict ACID compliance for versioning and provenance. A standard relational schema would likely satisfy these requirements. However, the physical database technology is **NOT** an architectural invariant.

**FUTURE RESEARCH / LONG-TERM POSSIBILITY: LLM Absorption**

It is a long-term possibility that a local LLM might absorb Azm knowledge so deeply into its weights that a distinct Azm database becomes unnecessary. The architecture described in these documents must remain valid even if the LLM strategy changes, which is why Azm retains its independent logical architecture.

**OPEN GAP / DECISION REQUIRED:** The exact physical database implementation details (tables, columns, indexes, vector embedding integration) are intentionally left open until the ingestion engine is implemented.
