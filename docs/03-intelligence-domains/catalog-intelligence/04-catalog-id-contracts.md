## 1. The Interaction Boundary

Catalog ID functions as a cognitive client to the authoritative Catalog Business System (`Catalog BS`). To guarantee zero direct database coupling, Catalog ID strictly uses approved contracts.

- **Discovery Phase:** Reads canonical facts via `vw_catalog_master` and related public views.
- **Command Generation Phase:** Submits mutations via the `SaveProductFamily` API contract.

---

## 2. Product Attachment & Mutation Contract

The command semantics generated by Catalog ID must explicitly target one of three operations. 

### 2.1 Operation: `NEW PRODUCT FAMILY`
- **Use Case:** Catalog ID determines the candidate represents a fundamentally distinct offering.
- **Supplied Identity:** None.
- **Proposed Identity:** `product_code` and `sku_id` (generated via heuristics).
- **Discovered Identity:** N/A.

### 2.2 Operation: `ATTACH NEW SKU TO EXISTING PRODUCT`
- **Use Case:** Catalog ID determines the candidate is a variant of an existing family.
- **CRITICAL INVARIANT:** Catalog ID **MUST** resolve the authoritative `product_internal_id` from Catalog BS. A matching `product_code` string is **NEVER** sufficient to force an attachment.
- **Supplied Identity:** `product_internal_id` (explicitly targeting the parent UUID).
- **Proposed Identity:** `sku_id`.
- **Discovered Identity:** `product_code` (used for discovery context, not as an anchor).

### 2.3 Operation: `UPDATE EXISTING SKU`
- **Use Case:** Modifying attributes of an already-published SKU (e.g., adding an image).
- **Supplied Identity:** `sku_internal_id` (explicitly targeting the SKU UUID).
- **Proposed Identity:** None (identifier changes are prohibited).

---

## 3. Historical / Stale Intelligence State

Catalog BS is a concurrent, multi-user system. Canonical data may change between the time Catalog ID starts an `IntakeSession` and when it generates a command.

- **Revalidation Requirement:** Before formulating the final mutation payload, Catalog ID must re-query the public read contracts to ensure its candidate context is not stale (e.g., ensuring a `sku_id` wasn't taken by another user during the session).
- **Enforcement Fallback:** If Catalog ID misses a concurrent update, Catalog BS's transactional locks and strict constraints will deterministically reject the payload. Catalog ID must handle this rejection gracefully (see Bounded Retries in `03`).
