# RABTA R-4.3 — CAPABILITY DISPATCH ARCHITECTURE AUDIT

## Final Status
**R-4.3 DESIGN READY FOR IMPLEMENTATION**

## 1. Purpose of R-4.3
R-4.3 establishes the central R-4 Capability Registry and dispatch architecture. It prevents `R4DiscoveryService` from growing into an unmaintainable monolithic conditional block, enforces hard boundaries between generic routing, application context, and business evidence, and introduces a formal mechanism to exhaustively prove capability coverage.

## 2. ID Terminology
To maintain architectural purity, identifiers are explicitly distinguished:
- **AaramIdentity:** The authentication/authorization identity of the calling application/user. This remains out-of-band context and must not pollute the CEM contract or applicability logic.
- **CEM ID / CEM URN:** The infrastructure routing identity of the selected CEM. Brain Core performs this selection. The CEM does not select itself based on application semantics, nor does it require routing identifiers in the payload.
- **Business ID:** The opaque physical identifier (e.g., UUID) of a business entity residing inside the CEM database. These are only passed back to Brain Core as opaque strings during resolution.
- **Semantic Reference:** The natural language/semantic representation supplied by Brain Core in the `AbstractEvidenceRequest`.

## 3. Authoritative R-4 Capability Registry
The architecture implements `R4CapabilityRegistry` as the authoritative internal dispatch map. Capabilities must implement an `IR4Capability` protocol exposing:
- `capability_urn`: The globally unique capability identifier.
- `supported_intent`: The operational intent (e.g., `RETRIEVE`).
- `required_semantics`: List of semantic entity constraints mandatory for execution (e.g., `inventory.entity.sku`).
- `optional_semantics`: List of optional entity constraints.
- `is_applicable()`: Predicate determining if the parsed `ConversationalUnderstanding` satisfies execution.
- `fetch_evidence()`: The read-only execution logic injecting physical dependencies.
The registry prevents capability drift by ensuring the class itself owns its structural metadata.

## 4. Capability Discovery vs. Capability Selection
The semantic request from Brain Core is abstract. **Capability Discovery** is the process of identifying which CEM capabilities *could* satisfy the request based on their required semantics. **Capability Selection** is determining which capability actually executes.
Inventory R-4 must not invent conversational intent. If an abstract request (e.g., `intent: RETRIEVE`, providing only `sku`) mathematically satisfies multiple capabilities (e.g., Ledger and Exception Status), R-4 cannot arbitrarily select one, as Brain Core owns conversational intent.

## 5. Multiple RETRIEVE Capability Response (The Ambiguity Rule)
The simplest, most contract-compliant behavior that preserves the Brain/CEM separation:
- If a semantic request mathematically satisfies **exactly one** capability: R-4 executes it and returns `EVIDENCE_AVAILABLE` with singular `evidence_data`.
- If a semantic request satisfies **multiple** capabilities: R-4 performs Discovery but refuses Selection. R-4 will **not** blindly merge evidence. Instead, it returns `status=EXECUTION_LIMITATION`, sets `reason="Ambiguous semantic intent. Multiple capabilities are applicable."`, and populates `capabilities_discovered` with the matched URNs. 
This decisively forces Brain Core (or the R-6 refinement layer) to narrow the user's intent.

## 6. Exhaustion and Certification Mechanism
A strict automated test (`test_r4_capability_exhaustion.py`) will programmatically assert that the `R4CapabilityRegistry` contains exactly the four capabilities identified in the R-4.3A Census:
- `urn:aarambooks:inventory:capability:balance`
- `urn:aarambooks:inventory:capability:ledger`
- `urn:aarambooks:inventory:capability:jobwork_status`
- `urn:aarambooks:inventory:capability:exception_status`

The test will also explicitly assert the absence of any future R-7 ACTION operations (Goods Receipt, Purchase Return, Transformation, Job Work Issue/Return, Exception Resolution) and internal operations (Balance Recalculation, Confidence Calculation, Master Data), strictly maintaining the boundary.

## 7. Existing Certifications (Balance & Ledger)
Balance (R-4.1) and Ledger (R-4.2) are already R-4 certified. The registry architecture will merely encapsulate their existing dispatch logic into `R4BalanceCapability` and `R4LedgerCapability` objects. Their internal business logic, R-5 dependencies, and testing boundaries remain absolutely untouched.

## 8. R-5 Semantic Boundary
`R4DiscoveryService` will centrally own R-5 (`SemanticResolverRegistry`). Capabilities themselves are strictly prohibited from implementing fuzzy matching, silent UUID casting, or conversational interpretation. Capabilities receive pre-resolved physical `business_ids` from the orchestrator.

## 9. R-7 Mutating Boundary
R-4 is strictly read-only. The `fetch_evidence` signature on the `IR4Capability` protocol will structurally forbid the injection of SQLAlchemy `AsyncSession` or mutating services. This mechanically prevents R-7 business operations from being accidentally registered.
