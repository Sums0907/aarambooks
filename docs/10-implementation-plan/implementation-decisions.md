# Implementation Decisions

## 1. Implementation Philosophy

The implementation of AaramBooks is strictly governed by the following core principles:

- **Architecture Before Code:** Implementation must follow documented and approved architecture. Assumptions must be validated against architecture documentation before any code is written.
- **Preserve Domain Ownership:** Ownership of capabilities is defined by business responsibility. Systems must not absorb responsibilities belonging to other domains.
- **Avoid Accidental Coupling:** Domains must interact through well-defined API contracts and events. Implementation details, databases, and internal logic must never be shared directly between domains.
- **No Duplicate Business Truth:** Business truth exists in one place. No system may implement a parallel operational database for data owned by another system.
- **Intelligence Enhances, It Does Not Replace:** Aaram Brain provides understanding and decision support. It does not replace the determinism, rules, and authority of Business Domain Systems.

---

## 2. Implementation Architecture Overview

The software structure mirrors the conceptual architecture to maintain alignment:

- **Business Domain Systems:** Transactional systems that maintain authoritative operational records and execute deterministic business processes.
- **Aaram Brain Core:** A generic, reusable foundation of intelligence capabilities that abstracts away AI infrastructure and provides reasoning, context, and memory components.
- **Intelligence Domains:** Business-focused applications that leverage Brain Core capabilities to solve specialized challenges (e.g., NDR, Customer Queries).
- **Shared Platform Capabilities:** Common infrastructure such as the event bus, API gateway, and model gateway, which facilitate communication without enforcing business logic.

Implementation must ensure strict logical (and eventually physical) separation between these layers.

### Initial Implementation Scope (Phase 1)
The initial phase of implementation is strictly scoped to establishing the foundational intelligence capabilities:
- Brain Core Foundation
- Customer Context Foundation
- Conversation Intelligence Foundation
- NDR Intelligence
- Customer Query Intelligence

---

## 3. Service Boundary Decisions

Service boundaries are non-negotiable and dictate where code lives.

### Business Domain Systems
These systems own operational business execution and truth.
- **AaramIdentity:** Owns authentication, authorization, roles, and permissions.
- **AaramInventory:** Owns product information, SKU data, inventory states, and stock ledgers.
- **AaramPacking:** Owns physical warehouse execution, packing workflows, and warehouse events.

### Aaram Brain Core
This system owns intelligence capabilities, not business processes.
- **Context Capabilities:** Understanding situational information.
- **Knowledge Capabilities:** Maintaining organizational rules and concepts.
- **Reasoning Capabilities:** Interpreting relationships and patterns.
- **Decision Capabilities:** Providing evaluated recommendations.
- **Action Capabilities:** Bridging intelligence to controlled execution.
- **Memory Framework:** Managing learning and interaction history.

### Intelligence Domains
These systems own specialized intelligence applications.
- **NDR Intelligence:** Intelligence applied to resolving delivery failures.
- **Customer Query Intelligence:** Intelligence applied to customer interactions.

**Boundary Enforcement:**
- Operational state must NOT move into Intelligence Domains.
- Business rules must NOT move into Brain Core.
- Intelligence processing must NOT move into Business Domain Systems.

---

## 4. Data Ownership and Storage Philosophy

Data storage implementation must strictly reflect architectural ownership:

- **Business Truth Ownership:** Stored exclusively in the database of the respective Business Domain System (e.g., Inventory DB belongs to AaramInventory).
- **Intelligence Data Ownership:** Data generated by reasoning or recommendations belongs to the Intelligence Domains.
- **Context Storage:** Transient storage for ongoing intelligence processing.
- **Conversation History:** Stored as interaction memory by Aaram Brain.
- **Memory Storage:** Long-term patterns and semantic embeddings stored in Brain Core.
- **Knowledge Storage:** Organizational rules and concepts accessible by the Knowledge Engine.
- **Decision History:** Logged by the Decision Engine for audit and explainability.
- **Audit Information:** Stored immutably for tracing AI decisions back to their context.

**Critical Rule:** Aaram Brain must not become a duplicate operational database.

**Customer Context Principle:** Operational customer truth (e.g., identity, explicit account details, order records) is owned strictly by business domain systems. AI customer context (e.g., semantic interaction history, inferred preferences, situational understanding) is owned by Aaram Brain. Aaram Brain maintains an understanding of the customer but does not become the authoritative database for core customer records.

**Governance for Caching:** If a domain requires caching for performance, the cache must be strictly ephemeral, explicitly marked as derived/stale representations, and never treated as the authoritative source of truth.

## 5. API Communication Strategy

Communication between boundaries relies on explicit contracts:

- **Synchronous Communication:** Used when an immediate response or intelligence outcome is required to continue a workflow.
- **API Contracts:** Define exactly what capabilities are exposed. They must not expose internal database schemas.
- **Request Ownership:** The consumer owns the intent and context of the request.
- **Response Ownership:** The provider owns the capability and the resulting data/action provided.
- **External Integrations:** External systems communicate via boundary gateways and are never allowed direct access to internal domain APIs.

**[OPEN DECISION]:** Specific API protocol standards (e.g., REST, GraphQL, gRPC) are yet to be finalized.

---

## 6. Event Architecture Strategy

Events decouple the ecosystem and propagate business truth asyncronously.

- **Why Events Are Required:** To allow intelligence systems to react to operational changes without creating synchronous bottlenecks or tight coupling.
- **Event Ownership:** Events are owned by the domain that produces them (e.g., AaramInventory owns "Stock Depleted" events).
- **Event Producers:** Responsible for publishing immutable facts about business changes.
- **Event Consumers:** Responsible for listening to events and applying their own domain-specific reactions.
- **Event Lifecycle:** Events are immutable historical facts. They cannot be altered once published.
- **Versioning Principles:** Changes to event structures must be additive and versioned to prevent breaking consumers.
- **Information Travels, Ownership Does Not:** Consuming an event grants access to the information, but not authority over the data.

**[OPEN DECISION]:** Event infrastructure (e.g., Kafka, SQS), payload standards (e.g., CloudEvents), and reliability expectations (Exactly-once vs At-least-once delivery) are yet to be finalized.

---

## 7. AI Provider Abstraction Strategy

AaramBooks retains complete ownership of its business intelligence, independent of third-party AI models. 

**External AI Infrastructure:**
- LLM Providers (e.g., OpenAI, Anthropic, Gemini)
- STT (Speech-to-Text) Providers
- TTS (Text-to-Speech) Providers
- SIP/Telephony Providers

**Aaram-Owned Intelligence:**
- Business reasoning and logic.
- Decision trees and rule engines.
- Workflow intelligence and state management.
- Customer understanding and context assembly.
- Business-specific automation rules.

**Boundary:** The **Model Gateway** abstracts all external AI infrastructure. Core intelligence logic must never be written in provider-specific DSLs (e.g., OpenAI Assistant APIs) that lock AaramBooks into a single vendor.

---

## 8. Integration Architecture

Future integrations must adhere to the ecosystem boundaries:

- **Inbound Integrations:** External triggers (e.g., customer messages, ShopDeck updates) must enter through a designated gateway, which routes them to the appropriate domain contract.
- **Outbound Integrations:** Ecosystem systems trigger external actions (e.g., Logistics updates) via dedicated integration adapters, keeping vendor-specific code out of core domains.
- **Webhook Philosophy:** Webhooks should be treated as untrusted inbound events. They must be validated and translated into internal ecosystem events before processing.
- **Event-Based Integrations:** Preferred for long-running, asynchronous cross-system workflows.
- **Specific Integrations:** ShopDeck, Logistics systems, Customer communication channels, and existing Aaram systems must all be integrated via these bounded adapters.

**ShopDeck Integration Boundary:** ShopDeck is an external operational system. It acts as an authoritative source of truth for its specific e-commerce operations. The AaramBooks ecosystem must interface with ShopDeck securely via integration adapters, but must never duplicate ShopDeck's operational truth into internal AaramBooks databases.

---

## 9. Security and Governance

- **Authentication Approach:** AaramIdentity is the single source of truth for authenticating actors (users, systems, and external integrations).
- **Authorization Boundaries:** Each domain enforces its own authorization rules based on the identity context provided by AaramIdentity.
- **Audit Requirements:** All AI-driven decisions and state-modifying actions must be logged immutably.
- **AI Action Governance:** Intelligence Domains can recommend actions, but critical business executions must be routed through controlled Business Domain workflows (and potentially require "Human-in-the-loop" approval).
- **Data Access Rules:** Domains cannot query other domains' databases directly. 
- **Sensitive Information Handling:** PII and sensitive data must be tokenized, masked, or strictly scoped before being processed by the Brain Core or external AI providers.

## 10. Implementation Decisions Still Open

The following physical implementation and technology decisions must be finalized before coding begins. 

### Backend Architecture Pattern
- **Decision Required:** Modular Monolith vs. Microservices.
- **Why it matters:** Dictates repository structure, deployment complexity, and module isolation enforcement.
- **Recommended Evaluation Criteria:** Team size, latency requirements, deployment overhead, and domain boundary enforcement tooling.

### Database Selection
- **Decision Required:** Relational vs. NoSQL vs. Vector/Graph Databases for specific domains.
- **Why it matters:** Brain Core (Memory/Knowledge) requires high-dimensional search, while Business Domains require ACID compliance.
- **Recommended Evaluation Criteria:** Read/write patterns, transaction requirements, and semantic search capabilities.

### Deployment Architecture
- **Decision Required:** Containerization, Serverless, orchestration (e.g., Kubernetes).
- **Why it matters:** Affects scalability, resilience, and operational overhead.
- **Recommended Evaluation Criteria:** Traffic predictability, cost, and developer experience.

### Event Infrastructure
- **Decision Required:** Event bus technology (e.g., Kafka, RabbitMQ, AWS EventBridge).
- **Why it matters:** Dictates event durability, replayability, and ordering guarantees.
- **Recommended Evaluation Criteria:** Throughput, retention requirements, and operational complexity.

### API Standards
- **Decision Required:** REST vs. GraphQL vs. gRPC.
- **Why it matters:** Defines how domains communicate synchronously.
- **Recommended Evaluation Criteria:** Payload size, schema enforcement, and client consumption flexibility.

### Observability (Monitoring & Logging)
- **Decision Required:** Tooling for tracing AI decisions and system health.
- **Why it matters:** Aaram Brain's non-deterministic nature requires deep, traceable context logging.
- **Recommended Evaluation Criteria:** Distributed tracing support, cost, and queryability.

### Testing Strategy & CI/CD
- **Decision Required:** How to test deterministic business logic alongside non-deterministic AI capabilities.
- **Why it matters:** Traditional unit testing is insufficient for LLM-based reasoning.
- **Recommended Evaluation Criteria:** Support for contract testing, deterministic mocking of the Model Gateway, and CI/CD integration speed.
